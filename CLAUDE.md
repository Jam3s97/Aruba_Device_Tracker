# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Home Assistant custom integration (`custom_components/aruba_device_tracker`) that polls an Aruba Instant AP's local REST API for connected Wi-Fi clients and exposes them as `device_tracker` entities, plus `switch`/`number` entities for runtime configuration. Based on the `integration_blueprint_template`.

## Commands

```bash
scripts/setup    # install runtime + test deps (requirements.txt, requirements-test.txt)
scripts/develop  # run a local HA instance with this integration loaded, config in ./config/
scripts/lint     # ruff format . && ruff check . --fix
scripts/test     # pytest tests/ -v
```

Run a single test: `python -m pytest tests/test_aruba_client.py::test_name -v`

Linting is `ruff` with `select = ["ALL"]` (see `.ruff.toml`) — expect strict enforcement (docstrings, type annotations, complexity limits). Test files get relaxed rules (see `[lint.per-file-ignores]`). Target is `py314`. Run `scripts/lint` before considering a change done; CI runs both lint and tests on every push/PR.

## Architecture

**Data flow:** `ArubaIAPClient` (aruba_client.py) logs into the IAP's REST API, session-authenticates, and runs `show clients` via the `show-cmd` endpoint, parsing the CLI table output into a `dict[mac, ArubaClientData]` (a `TypedDict`). `_parse_clients` finds the header line and slices each row at its headings' character offsets (`_find_columns` / `_slice_row`): Aruba tables are left-aligned, so this keeps a blank cell blank. Splitting on whitespace does not. The old single-token regex, `_CLIENT_REGEX`, shifted every later field left when a column was empty (a client with no OS fingerprint showed its SSID as OS and its channel as AP). Columns are looked up by normalised heading with aliases (`IP Address`/`IP`, `Speed (mbps)`/`Speed`), since firmware versions name them differently. `_CLIENT_REGEX` is only a fallback: for output with no recognisable header, and per row when a sliced row fails MAC/IPv4 validation, so odd formatting degrades to the old behaviour instead of dropping a present device (which would mark it away). `get_aps` runs `show aps` on the conductor (the configured host, normally the Virtual Controller IP, which reports every AP in the cluster) and returns `dict[serial, ArubaAP]`, built with the same column parser (`_parse_aps`, with no regex fallback). APs are keyed by **serial number** because `show aps` has no MAC column. The conductor's IP has a trailing `*`, which becomes `is_conductor`. `ArubaAP` deliberately leaves out the volatile columns (`Age`/uptime, radio utilisation, noise). Clients link to APs by **name**, because the `show clients` `Access Point` column holds the AP name. `get_networks` runs `show network` (`_parse_networks`, `dict[profile, ArubaNetwork]`), which lists every *configured* network, quiet and disabled ones included. Networks are keyed by **profile name**, which survives an SSID rename. Clients report the broadcast **ESSID**, which can differ from the profile (for example a `Visitors` profile broadcasting `VisitorNet`, as in the fixture). `get_aps` and `get_networks` share `_get_table`. A non-Success `show-cmd` status warns once per command and then logs at debug until that command succeeds again (`_refused_cmds`): a refusal is usually permanent, such as an account without the privilege for `show aps`, and it would otherwise warn every poll. `ArubaIAPCoordinator` (`__init__.py`, a `DataUpdateCoordinator[dict[str, ArubaClientData]]` subclass) polls this on `scan_interval` and holds the latest snapshot as `coordinator.data`. Entries are typed as `ArubaConfigEntry = ConfigEntry[ArubaIAPCoordinator]`, and the coordinator is reached via `entry.runtime_data`.

**Error contract:** the client raises `ArubaAuthError` / `ArubaConnectionError` / `ArubaCertificateError` (all `ArubaError`) rather than returning bools. `async_setup_entry` maps these to `ConfigEntryAuthFailed` (starts the reauth flow in `config_flow.py`), `ConfigEntryNotReady` (HA retries with backoff) and `ConfigEntryError` (permanent — retrying an untrusted certificate can never succeed). Inside `_show_cmd`, connection-class failures stay *soft* — log at debug, clear the session id, return `None`, keep last-known data — while `ArubaAuthError` and `ArubaCertificateError` propagate, the former so the coordinator can trigger reauth, the latter because it is a configuration problem needing user action. `ArubaCertificateError` is deliberately **not** a subclass of `ArubaConnectionError`, which is what keeps it out of that soft path. "Keep last-known data" covers blips only: the coordinator counts consecutive `None` results and, at `UNAVAILABLE_AFTER_FAILED_POLLS` (3), raises `UpdateFailed`. HA keeps `coordinator.data` on a failed refresh, logs the outage once and the recovery once, and `ArubaClientEntity.available` follows `last_update_success`, so trackers go unavailable instead of showing stale state for the whole outage. Any successful poll resets the count. The per-poll message in `_show_cmd` is debug-level for the same reason: during an outage it would otherwise warn every poll. The other exception is the first refresh, where there is no last-known data at all: the coordinator raises `UpdateFailed` (so setup retries via `ConfigEntryNotReady`) instead of returning `{}`, which would flip every restored device to away. A failed first refresh also logs out and closes the client inside `async_setup_entry`, because `async_unload_entry` never runs for a failed setup. Never interpolate a raw `requests` exception into a user-visible message: the IAP takes `sid` as a URL query parameter and requests embeds the URL in its exception text. `ArubaIAPClient._redact` exists for this.

**Entities read from the coordinator, they don't fetch data themselves:**
- `device_tracker.py` — `ArubaClientEntity` per MAC. `is_connected` reflects presence in `coordinator.data`; entities for *offline* devices still exist (seeded from `coordinator.last_seen`) so devices correctly restore as "away" instead of "unavailable" on HA restart. `unavailable` is reserved for "the AP itself can't be read" (see the error contract): a device missing from the client list is always away.
- **Tracker unique IDs are entry-scoped:** `utils.tracker_unique_id(entry_id, mac)` → `f"{entry_id}_{mac}"`, returned by an overridden `ArubaClientEntity.unique_id` (`ScannerEntity`'s default returns the bare MAC and ignores `_attr_unique_id`). HA requires unique IDs to be unique across the whole integration, so with bare MACs a second AP entry that saw the same device had its entity dropped with a "does not generate unique IDs" error. Now each AP gets its own tracker (`device_tracker.phone`, `device_tracker.phone_2`) and a person entity combines them. `mac_address` stays the bare MAC, since that is what links the tracker to other integrations' devices. Entry version 1.2 (`MINOR_VERSION` in `config_flow.py`); `async_migrate_entry` rewrites 1.1 bare-MAC unique IDs in place via `er.async_migrate_entries`, which keeps entity IDs, names and history. A downgrade to 2.0.x after migrating would create a duplicate entity per device, because the old code looks for bare-MAC IDs.
- `sensor.py` / `binary_sensor.py` — **AP devices** (the `enable_ap_devices` option, default on in the 2.2 beta). Each AP gets a device built by `utils.get_ap_device_info`: `identifiers={(DOMAIN, serial)}`, `serial_number`, and no MAC connection (`show aps` has none, so it never merges with another integration's device). There is deliberately **no `via_device`** link to the control device: HA 2026.9 deprecates `via_device` (removed in 2027.8) in favour of `via_device_id`, which the 2026.3 floor doesn't have. Add `via_device_id` once the floor reaches 2026.9. Per-AP entities subclass `entity.ArubaAPEntity` (unique ID `utils.ap_unique_id(entry_id, serial, key)`, entry-scoped like trackers, no attributes) and are created by `entity.async_setup_ap_entities`:
  - **Connectivity** (`binary_sensor`, `CONNECTIVITY`). On while the AP is in `coordinator.aps`. **Off** when `show aps` succeeded but the AP's row is missing: `show aps` has no status column, and an AP that loses power simply drops out (measured on a 6-AP cluster, 2026-10-23: 53–88s after power was cut, plus up to one poll interval before the sensor updates). Unavailable only when the AP list can't be read (`last_update_success and aps_ok`). Mode is ignored on purpose: a booting AP is listed as `monitor` for about 15s, with a blank Clients cell and `-` radio channels, before `access` (it reappeared about 3 minutes after power-on: 2m59s in the run with exact times), and `monitor` is also a deliberate air-monitor mode.
  - **Clients** (`sensor`, `MEASUREMENT`). Available only while the AP is listed (`ArubaAPEntity.ap_listed`), so an offline AP's count is unavailable rather than a misleading 0.
  - `async_setup_ap_entities` seeds entities from the **device registry** as well as the live list, so an AP that is off when HA starts reads Disconnected rather than having no entities, the same way trackers are seeded from `last_seen` so offline devices restore as away. A registry-only AP's `DeviceInfo` omits name and model, so the registry keeps them. A coordinator listener adds APs first seen on later polls. Each entity calls `forget(serial)` when it is removed, so an AP whose device was deleted and which later comes back gets new entities instead of being skipped as known.
  - **Total clients** (`len(coordinator.data)`) sits on the control device.
  - An AP that drops out keeps its device (a rebooting AP keeps its name and area). `async_remove_config_entry_device` lets the user delete it once it has gone, and refuses APs still reporting, the control device and tracker devices (`utils.is_ap_device` tells them apart: trackers' devices carry only a MAC connection, and the control device's identifier is the entry id).
- **Cluster subentry (device grouping).** HA lists a config entry's devices grouped by config subentry, and always draws its own "Devices that don't belong to a sub-entry" section *first* (fixed in the frontend; it can't be renamed or reordered). That section is where the devices HA links to trackers by MAC end up (another integration's camera or vacuum). To keep this integration's own devices apart from them, `_async_ensure_cluster_subentry` creates one subentry in code (`CLUSTER_SUBENTRY_TYPE`, id `access_points`, which predates the rename and stays so existing groups aren't orphaned; title "Controller and access points", type label "Aruba Instant cluster"), with no subentry flow, so users can't add one. It holds the **IAP control device and every AP device**, and exists whether or not the AP option is on. Its `config_subentries.access_points` translations must include `initiate_flow` and `step` as well as `entry_type`, because hassfest's schema requires all three for every subentry type. Only `entry_type` (the group's second line) is ever shown, since the integration offers no subentry flow. `tests/test_translations.py` checks this locally, so a missing key doesn't first show up as a CI failure. Every non-tracker platform passes `config_subentry_id=coordinator.ap_subentry_id` to `async_add_entities` (switch, number, Total clients and the AP entities). Tracker entities must **not** be in it: HA would put their linked devices in it too.
  - **Migration**, on every setup: `_async_remove_devices_outside_subentry` removes this integration's own devices (any identifier in our domain) that aren't in the subentry. That means the IAP device on installs from before it, and 2.2.0-beta.1's AP devices. Their entities go with them and are recreated inside the subentry as the platforms add them. Delete-and-recreate is used because it works on both HA versions (moving a device needs `new_config_subentry_id`, 2026.9+ only). Entity IDs come back the same, because they're generated from the same names and the registry restores deleted entries' settings by unique ID, so history carries on. Verified live: 17 entities, identical IDs. A device's area or custom name is lost once.
  - **Deleted in the UI:** deleting a subentry makes HA remove every device and entity in it, the IAP device included, while the entry stays loaded. `_async_cluster_subentry_listener` (an update listener that acts *only* when the subentry has gone, so not a reload-on-every-options-write listener) clears `ap_subentry_id`, which stops the AP platforms adding to it, then turns the AP option off and schedules a reload. Setup recreates the group with just the IAP device.
  - Reading a device's entry and subentry in a version-agnostic way: `utils.device_in_subentry` and `utils.device_only_in_entry`. HA 2026.9 made a device belong to one config entry and subentry (`config_entry_id` / `config_subentry_id` fields), and 2026.10 deprecates the old multi-entry attributes (`config_entries`, `config_entries_subentries`, `primary_config_entry`, removed in 2027.10), which are plain fields on the 2026.3 floor. The helpers check for `config_subentry_id` / `config_entry_id` first, so the deprecated names are never read on new HA. The test fakes' default devices have only the new fields (`device(..., legacy=True)` builds the 2026.3 shape), so a stray use of the old names fails a test.
- **AP polling** lives in the same coordinator, not a second one. `_async_update_aps` runs `get_aps` *after* a successful `get_clients` in the same poll, never in parallel (one HTTP session and login, and management-plane load is the usual cause of failed polls), and is skipped when `get_clients` returned `None`. Its failures are isolated: `None`, `ArubaError` or an unexpected exception set `aps_ok = False` and keep the last-known `aps`, while client data, last-seen and presence update normally. The only exception is `ArubaAuthError`, which raises `ConfigEntryAuthFailed`. `coordinator.data` keeps its type. AP data sits beside it (`aps`, `aps_ok`, `ap_client_counts`). Counts come from the client list grouped by AP **name** → serial, so the sensors agree with the trackers. The AP-reported `Clients` column is compared at debug level only, since the two commands are moments apart. Duplicate AP names warn once. A controller rename updates the device name explicitly (`DeviceInfo` is only applied when an entity is added), and `name_by_user` still wins.
- **Clients per network** (`sensor.py`, `ArubaNetworkClientsSensor`, on the IAP device in the cluster subentry, always on, no option). `_async_update_networks` fetches `show network` at most every `NETWORK_REFRESH_MINUTES` (30), after `show clients` and `show aps`, never in parallel. A failed fetch is retried on the next poll rather than after the full interval. Failures are isolated (`networks_ok`) through the same `_async_fetch_table` helper as `show aps`. `network_client_counts` is recounted **every poll** from the client list, ESSID → profile. Duplicate ESSIDs warn once. The controller's own Clients column is compared at debug level only right after a fetch, because between fetches it is stale. Unique ID `utils.network_unique_id(entry_id, profile)`. The name is `translation_key="network_clients"` with an `{essid}` placeholder read live from `coordinator.networks`, so an SSID rename renames the sensor. Available only while the network is listed, enabled and `networks_ok`, so a disabled network reads unavailable, not 0. The platform (`_async_setup_network_sensors`) adds sensors for new profiles, and **removes a profile's sensor once a successful fetch no longer lists it** (deleted on the controller). A failed fetch never removes anything. If the first fetch fails, registered sensors are seeded from the entity registry so they read unavailable instead of vanishing. The coordinator holds no registry code.
- **Area sensors** (`sensor.py`, `ArubaClientAreaSensor`, only while `ap_devices` is on). One per **enabled** tracker, mirroring the trackers: seeded from `last_seen` plus live clients, added on later polls, and forgotten through `coordinator.async_add_removal_listener` when stale cleanup removes a client. A tracker counts as enabled if its registry entry has `disabled_by is None`, or, when it isn't registered yet (it's about to be created), if Track new devices is on, which is what decides its `entity_registry_enabled_default`. A disabled tracker's client isn't recorded as known, so it is re-checked. Enabling or disabling a tracker makes HA reload the entry, which re-runs setup, and setup removes leftover Area sensors whose tracker is disabled so they don't linger as "no longer provided". `_add` records each sensor as it builds it, because a client that is both remembered and connected appears twice in the seed list (this was a bug: a duplicate unique ID). `entity_registry_enabled_default = False` always, so users enable the few they want. The `enable_area_sensors` option is **off by default** (opt-in). Turned on, it creates the sensors, each still disabled. It is read once at setup as `coordinator.area_sensors = ap_devices and option`, because they need AP devices for their areas. Setup calls `_async_remove_area_sensors` when it's off with AP devices on (`_async_remove_ap_devices` calls it too). Resolution: client `access_point` name → `coordinator.ap_serial_by_name` (kept by `_count_clients_per_ap`) → AP device via `utils.find_ap_device` → `area_id` → area registry. **Never `dr.async_get_device`**: HA 2026.9 deprecates it (identifiers are only unique per config entry), and its replacement `async_get_device_by_identifier` doesn't exist on 2026.3. `find_ap_device` scans this entry's own devices, which works on both. The test fake's `async_get_device` raises, to catch new uses. The state is the area **name**. Attributes: `mac`, always present and identical to the tracker's own `mac` attribute (it links the two, since the sensor has no device, and two trackers can share a name when a phone uses a private MAC per SSID; it is static, so no recorder rows), and `area_id` while an area is known. Unknown when away, on an AP that isn't listed, or on an AP without an area. **No device and no subentry**: a client entity in the cluster subentry would pull tracker-linked devices into the group, and a device per phone would be clutter. So `has_entity_name` is False and the name is `"<tracker name> area"`, fixed at creation (live name → tracker registry name, including a user-set one → MAC). Redrawn on coordinator updates and on `EVENT_DEVICE_REGISTRY_UPDATED` (filtered to `area_id` changes, `_area_changed`) and `EVENT_AREA_REGISTRY_UPDATED`. Unique ID `utils.area_unique_id` = `f"{entry_id}_area_{mac}"`, a **prefix**, so a network profile named "area" can't collide (`is_area_unique_id`). Removed with its tracker by `_async_cleanup_stale_devices`, and by unique ID in `_async_remove_ap_devices` (no device, so device removal doesn't cascade to it). It writes a recorder row per change of area, so per roam, not per poll.
  - **Repairs notice** `aps_without_area_{entry_id}` (warning, not fixable, `{aps}` placeholder). Raised only while at least one Area sensor is enabled (added to hass) and a listed AP's device has no area. Re-checked on every poll and registry event, and deleted on unload, so turning AP devices off clears it.
- **Conditional platforms:** `AP_PLATFORMS` (`[BINARY_SENSOR]`) is forwarded only when the option is on. `SENSOR` is in `BASE_PLATFORMS`, because Total clients counts the client list and needs no `show aps`. The per-AP Clients sensors on it are only added while `coordinator.ap_devices` is set. `coordinator.platforms` records what setup forwarded, and `async_unload_entry` unloads exactly that: reading the option at unload would break the reload that toggling it triggers. Every entity on `AP_PLATFORMS` belongs to the feature, so `_async_remove_ap_devices` removes this entry's `AP_PLATFORMS` entities by domain, and its AP devices with `async_remove_device`. HA removes a device's entities with it (`EntityRegistry.async_device_modified`, verified on both 2026.3 and 2026.9), which clears the per-AP Clients sensors while Total clients, on the IAP device, stays. Since HA 2026.9 a device belongs to a single config entry: lookups are per entry, so two entries for the same cluster get separate AP devices, and `add_/remove_config_entry_id` are deprecated (removed in 2027.8). A device that still lists several entries can only exist on older HA, so only then is the entry detached with `remove_config_entry_id`. It runs on **every** setup with the option off, not only on the toggle, so it is idempotent and covers downgrades and half-finished reloads.
- `switch.py` / `number.py` — control entities (track-new-devices toggle, cleanup enabled/days, etc.) attached to a synthetic "IAP control device" (`utils.get_device_info`), not to any tracked client. They read their state from `entry.options` and subclass `entity.ArubaOptionsEntity`, which registers an update listener so Configure changes redraw the controls, and sets `EntityCategory.CONFIG`. That lists them under the device page's Configuration section and keeps them out of auto-generated dashboards and of voice commands like "turn off all switches". `enable_ap_devices` / `enable_area_sensors` are deliberately **not** entities: they add or remove devices and entities after a reload, which shouldn't be one dashboard tap or voice command away. Both are asked in the config flow's tracking step (saved to `entry.data`, read through `_option()`) and changed under Configure. When track-new changes from off to on, either from the switch or Configure, the track-new listener re-enables only trackers with `disabled_by is RegistryEntryDisabler.INTEGRATION` (what HA records when `entity_registry_enabled_default` was False); `USER`, `DEVICE` and `CONFIG_ENTRY` are never touched, so a tracker the user hid stays hidden.

**Recorder write volume (why attributes look sparse):** HA writes a recorder row whenever an entity's state *or any attribute* differs from the previous one — `StateMachine.async_set` early-returns and fires only `EVENT_STATE_REPORTED` when both match, and the recorder subscribes to `EVENT_STATE_CHANGED` only. A tracker's state changes rarely, so attributes drive database growth: one per-poll attribute = one row per device per poll (~2,880/day/device at the default 30s interval).

`ArubaClientEntity.extra_state_attributes` is therefore built so a device whose situation is unchanged produces *no* rows:
- `signal` and `speed` are **not published**. The parser still reads them and `ArubaClientData` still carries them (the regex fallback needs those columns to match the row layout, and they're useful in debug logs) — they're just never surfaced as attributes, because their values move almost every poll.
- `last_seen` / `days_until_cleanup` are published **only while the device is away**. For a connected device `last_seen` is by definition ~now, so it changed every poll while conveying nothing the `home` state didn't. Away devices have a frozen timestamp, so both attributes are stable.
- What's left (`access_point`, `essid`, `ip_address`, `os`, `channel`) only moves on a real change: roam, new IP, band switch.

`tests/test_device_tracker_attributes.py::TestRecorderChurn` pins this invariant — notably that changing `signal`/`speed` in coordinator data leaves the attribute dict byte-identical. Don't add a per-poll attribute without re-reading this; it is a silent, compounding cost that no test other than those will catch. Removing `signal`/`speed` and gating `last_seen` was a deliberate breaking change in 2.0.0, documented in the README.

`Entity._unrecorded_attributes` is **not** a fix for this: it only strips the listed keys from the hash-deduplicated `state_attributes` blob, while the recorder still inserts a `states` row for every `state_changed` event. It shrinks rows, not row count — only worth pairing with a volatile attribute that must be live in the state machine, which a separate opt-in sensor entity does better.

**Persistent last-seen storage:** `coordinator.last_seen` (`dict[mac, iso_timestamp]`) is loaded/saved via HA's `Store` helper independently of the entity/device registries, so it survives restarts. The storage key is **per config entry** (`f"{DOMAIN}.{entry_id}.last_seen"`) — a shared key made two APs overwrite each other; `LEGACY_STORAGE_KEY` in const.py is the pre-2.0 shared key, still read once by `_async_migrate_legacy_store` to adopt existing installs (the old file is left in place). Writes go through `Store.async_delay_save` (`STORAGE_SAVE_DELAY`), never `async_save` on every poll. `last_seen` is loaded in `async_setup_entry` *before* `async_config_entry_first_refresh`, and is the source of truth both for seeding offline entities at startup and for stale-device cleanup.

**Stale-device cleanup:** `_async_cleanup_stale_devices` removes entity-registry entries — not just marks them unavailable — once a MAC hasn't been seen for `cleanup_days`. It is throttled to `CLEANUP_INTERVAL_HOURS` (staleness is measured in days, so a registry scan every poll buys nothing). It looks entities up by the entry-scoped unique ID (see below), so it can never match another AP's entity for the same MAC. Removals are broadcast to `coordinator.async_add_removal_listener` subscribers so `device_tracker.py` can drop the MAC from its `tracked` set — otherwise a cleaned-up device that reconnected would never get a new entity.

**Diagnostics** (`diagnostics.py`): the download includes the raw `show aps` and `show clients` tables, read from `ArubaIAPClient.last_outputs` (the last successful output of each command). It never sends its own request, because one running beside a poll would share the session and could race the re-login. `async_redact_data` can't scrub these tables, since it works on dict keys and each table is one string. So `_Scrubber` replaces every cell in an identifying column (`_CLIENT_FAMILIES` / `_AP_FAMILIES`: names, IPs, MACs, IPv6, SSIDs and roles, AP names, serials, zone) with a placeholder **padded to the cell's width**. Column offsets survive, so a scrubbed table parses exactly like the original, blank cells and the conductor `*` included, which is what a parser bug report needs. Placeholders are consistent across both tables (an AP name maps to the same `AP-n` in each) and come from documentation ranges (`192.0.2.x`, `2001:db8::`, MAC `00:00:5e:00:53:xx` per RFC 7042). A regex safety net catches any MAC or IPv4 address outside those columns. Output with no recognisable table is reduced to its shape (letters → `a`, digits → `9`), because nothing in it is known to be safe. Tests compare cells row by row instead of searching for the original values, because the committed fixtures are anonymised in the same style as the placeholders. The `ap_model.yml` issue template asks users for the download.

**Config/options split:** Settings (host/credentials, scan interval, track-new, cleanup enabled/days, verify_ssl) are readable from either `entry.options` (runtime-changeable) or falling back to `entry.data` (set-once at config-flow time), via the pattern `entry.options.get(KEY, entry.data.get(KEY, DEFAULT))` — wrapped as `_option()` in `__init__.py` and used consistently in the coordinator and the switch/number entities. "Runtime-changeable" means read at the moment of use, never captured at setup: `track_new` is read inside `device_tracker._new_entities_for` on every call (it decides `entity_registry_enabled_default`, which HA only consults when it first registers an entity), and capturing it once in `async_setup_entry` made the switch and Configure ineffective until a reload. There is deliberately **no** reloading `update_listener` for options changes — see the long comment in `__init__.py`'s `async_setup_entry`: switch/number entities write straight to `entry.options`, and reloading on every options write previously caused spurious "entity no longer provided" banners. Connection settings (host, credentials, `verify_ssl`) are changed only through the **reconfigure flow** (`async_step_reconfigure`), which tests the connection, writes them to `entry.data`, and reloads via `async_update_reload_and_abort`. It also strips any `verify_ssl` from `entry.options`: older versions' options flow stored it there, and since options are read first, a stale copy would override the new value. The options flow holds only the tracking settings plus `enable_ap_devices`. It returns `async_create_entry` with the existing options merged in (so keys it doesn't show survive) and applies a changed poll interval to the coordinator directly. `enable_ap_devices` and `enable_area_sensors` (`config_flow.RELOAD_OPTIONS`) are the only options that need a reload, because they decide which platforms and entities are set up. The options flow handles that itself, and only when one of them changed: it calls `async_update_entry` and *then* `async_schedule_reload`, because HA starts the reload task eagerly (`eager_start`), so scheduling before saving would set up again with the old value. `OptionsFlowWithReload` is not an alternative: it reloads on every save, and HA raises if the entry has update listeners, which `ArubaOptionsEntity` registers.

**TLS:** certificate verification is controlled by the `verify_ssl` option and defaults to **off**, because Instant APs ship a self-signed certificate. `urllib3.disable_warnings` is called lazily (once per process, only when an unverified request is actually made) rather than at import time, so installing this integration doesn't silence TLS warnings for the whole HA process.

When verification is on and the AP's certificate can't be validated, `_request_once` turns the `CERTIFICATE_VERIFY_FAILED` `SSLError` into `ArubaCertificateError` carrying an actionable message, and the config flow surfaces it as the `invalid_cert` error key instead of the misleading `cannot_connect`. The raw `SSLError` is never logged with a traceback — the cause is known and the urllib3/ssl stack is ~90 lines of noise.

Separately, `aruba_client.py` handles Instant AOS firmware whose TLS stack needs legacy renegotiation (`UNSAFE_LEGACY_RENEGOTIATION_DISABLED` on modern OpenSSL). `_LegacyTLSAdapter` is mounted only after that specific SSLError is actually observed, then stays active for the life of the client instance. Renegotiation and verification are orthogonal: the adapter relaxes only the renegotiation flag and honours `verify_ssl` for cert checking.

## Testing conventions

- `tests/conftest.py` defines the fake AP host/port/URLs and fixtures (`client`, `logged_in_client`, `raw_output`); `requests_mock` (via `requests-mock`) mocks the REST endpoints — no real network/AP needed.
- `tests/fixtures/*.txt` hold raw `show clients` / `show aps` / `show network` CLI output samples used to test the parser against real-world formatting edge cases (empty names, missing speed column, an SSID containing a space, etc.). `show_clients_real.txt`, `show_aps_real.txt` and `show_network_real.txt` are anonymised captures from the same real 6-AP cluster, taken over REST, so their AP names and SSIDs match. `show_network_real.txt` keeps the stray carriage-return line the REST API sends after `COMMAND=`, and two profiles whose name differs from their ESSID. The clients capture includes a row with a blank OS column. Anonymise any new capture before committing it (MACs, IPs, hostnames, SSIDs, serials), and rebuild the table so the columns still line up, because the parser depends on the offsets.
- `tests/conftest.py` also holds the shared registry fakes: the `dev_reg`, `ent_reg` and `area_reg` fixtures patch HA's registry helpers, and the autouse `issues` fixture records Repairs issues instead of writing them, because any poll that reaches the Area sensors' platform raises or clears one.
- Entity-level tests (e.g. `test_device_tracker_attributes.py`) use a minimal `FakeCoordinator` dataclass rather than spinning up Home Assistant, since entities only read from the coordinator's public attributes.
- `test_coordinator_cleanup.py` follows the same philosophy for coordinator logic: it builds a *real* `ArubaIAPCoordinator` via `object.__new__`, assigns fakes for `hass`/`Store`/`config_entry`, patches `er.async_get`, and drives the coroutines with `asyncio.run`. There is no `pytest-asyncio` or `pytest-homeassistant-custom-component` in `requirements-test.txt` — adding the latter is the prerequisite for testing the config/options/reauth flows and real `Store` migration end to end.

## Deferred decisions

Things deliberately left alone, with the reasoning, so they get re-decided rather than re-discovered.

### Tracked-devices subentry (future feature, needs a 2026.9 floor)

Wanted: put the devices HA links to trackers by MAC (another integration's camera, vacuum, AC) in a second subentry, e.g. title "Tracked devices", type label "Also in other integrations". The integration page would then show only our two groups, Controller and access points on top, with our own labels, and HA's fixed "Devices that don't belong to a sub-entry" section would disappear. Decided 2026-10-23 to keep the 2026.3 floor for 2.2 and build this once the floor is raised to 2026.9 (it is the first concrete reason to raise it). Why it waits:
- On 2026.3, `ScannerEntity` links a tracker by adding our config entry to the other integration's device with `add_config_entry_id` and **no subentry**, so those devices can't be grouped there at all.
- On 2026.9, `ScannerEntity` creates its own device with `config_subentry_id=registry_entry.config_subentry_id`, so adding trackers under a subentry groups their devices. But existing linked devices (no subentry) would be "silently moved" by `async_get_or_create`, which reports a deprecation in our name and raises in 2027.8. They must be moved explicitly with `async_update_device(new_config_subentry_id=...)`, which only exists from 2026.9.
- To build: raise `hacs.json` and `requirements.txt` together. Add tracker entities with the subentry id. Move existing tracker entities (`async_update_entity(config_subentry_id=...)`) and their linked devices (`new_config_subentry_id`). Create the cluster subentry first, so it sorts first. Add a deletion guard like `_async_cluster_subentry_listener`, because deleting this group would remove **every tracker entity** (recreated on reload with IDs and history kept, but alarming).
- The same floor raise also allows `via_device_id` on AP devices and drops the shared-device branch in `_async_remove_device`.
- Install share when decided (HA analytics, 2026-10-23): 2026.3+ 86%, 2026.6+ 80%, 2026.9+ 66%.

### Single HA version for dev and floor (revisit)

`requirements.txt` and `hacs.json` both pin `homeassistant==2026.3.2`, and they are kept equal on purpose. `hacs.json`'s `homeassistant` key is the minimum version HACS enforces as an install gate for end users; `requirements.txt` is what CI and `scripts/develop` install. Keeping them equal means CI actually tests the version users are promised.

A dev-on-latest / floor-on-oldest split was tried and reverted. It is the better long-term setup — newer cores emit the deprecation and `frame.report_usage` warnings that are the main early warning for breaking changes, which is how the coordinator `config_entry` issue was found — but it is only safe once **CI verifies both ends**. Right now nothing does, so a split silently turns the `hacs.json` minimum into an unverified claim: green CI while shipping a newer-only API to users on the floor version.

Revisit when worth the CI change. What it needs:
- A test matrix in `.github/workflows/test.yml` over `[floor, dev]`, installing `requirements.txt` then overriding the HA pin per matrix entry.
- The floor read from `hacs.json` (`jq -r .homeassistant hacs.json`) rather than duplicated, so the two cannot drift.
- `dependabot.yml` already ignores `homeassistant` so it stays matched to `hacs.json`; a split needs that reasoning revisited too.
- Decide how wide the support window should actually be. 2026.3 -> 2026.9 is ~6 months, which is only worth claiming if it is genuinely tested.

Verified 2026-09-29: the integration passes its full suite and imports cleanly on **both** 2026.3.2 and 2026.9.4, and every HA API it uses (`_get_reauth_entry`, `async_update_reload_and_abort(data_updates=...)`, coordinator `config_entry=`, `Store.async_delay_save`, `TextSelectorType.PASSWORD`) exists on the 2026.3.2 floor.

Verified again 2026-10-23 for 2.2.0-beta.1: the full suite (170 tests) passes on both 2026.3.2 (a scratch virtualenv from `requirements.txt`) and 2026.9.4 (the dev container, which has drifted from the pin). 2026.9 is where the gap shows: it deprecates device-registry `via_device` and `add_/remove_config_entry_id` (both removed in 2027.8), and its `DeviceInfo` has `via_device_id`, which 2026.3.2 lacks. The AP feature avoids both deprecations (see Architecture). That is the kind of drift the dev/floor CI matrix would catch automatically.

### pytest-homeassistant-custom-component (parked)

Not added. It is the only practical way to cover the config flow, options flow, reauth flow and the real `Store` per-entry migration, which currently have no automated tests. Costs measured 2026-09-29:
- Pins `pytest` exactly and conflicts with this repo's pin (`pip install phcc==0.13.318 pytest==9.1.1` -> `ResolutionImpossible`); PHCC must own the pytest version.
- Pins `homeassistant==` exactly, one release per HA release, which fights the deliberate HA pin. Dependabot runs daily on pip and would bump PHCC (and therefore HA) unless PHCC is added to the ignore list beside `homeassistant`.
- ~30 transitive deps (SQLAlchemy, numpy, pydantic, paho-mqtt, syrupy, respx, pytest-xdist).
- Breaks 25 of 63 existing tests on install: its autouse fixtures call `asyncio.get_event_loop()`, and `test_coordinator_cleanup.py` uses bare `asyncio.run()`, which closes the loop. Client (37) and entity (10) tests are unaffected — so the work is converting those 16 tests to `pytest-asyncio`, not a compatibility wall.

If picked up: match the PHCC release to the pinned HA version (`0.13.318` for 2026.3.2), drop the explicit `pytest` pin, set `asyncio_mode`, add PHCC to the dependabot ignore list, and convert the `asyncio.run()` tests.
